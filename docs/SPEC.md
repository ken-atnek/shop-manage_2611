## 制作・実装方針

- デザイン実装プロジェクトは1つとし、Master / Clientの基本UIを共通化する
- 制作の流れ：Codexがプロンプトの依頼範囲で制作用PHP（HTML部分）・Sassを作成し、ユーザーが必要な箇所を調整し、Claudeが確認する。Codexは依頼範囲外のPHP・HTMLを作成・変更しない
- 静的HTML・Sassをブラウザで確認しながらデザインを固める
- 制作時はDDEVのPHPで共通ヘッダー・サイドバーをインクルードする。HTMLの組み立てにNodeは使わず、PHPは表示の共通化・現在地・静的出力時のリンク切り替えだけに限定する
- 制作用PHP（include構成）・Sass・生成CSSをバックエンド担当者へ渡し、Laravel・Bladeへの組み込みは担当者が行う。静的HTMLは納品物に含めない
- フロント（デザイン実装）の作業ではLaravelを構築しない。Laravelの構築・組み込みはバックエンド担当者が同じリポジトリで行う
- Figmaは必須工程ではなく、必要な場合のみ使用する
- Vite・Astroは現時点では使用しない

## フォルダとSass

- ルートの `index.html` は制作確認用のページ一覧で、納品しない。画面の追加や状態の変更のたびに更新する
- `scss/`：`@use`で読み込むreset・変数・既存の関数やmixinなど。単独のCSS出力対象にしない
- `shop-master/`：Master用の静的HTMLとアセット。対象URLは`https://shop-master.kumanichi.com/`
- `shop-partner/`：Client用の静的HTMLとアセット。対象URLは`https://shop-partner.kumanichi.com/`
- `docs/`：仕様・デザイン方針・実装引き渡し資料
- `.agents/`：プロジェクト専用スキル
- `backend/`：バックエンド（Laravel）のコード。バックエンド担当者が使う
- `shop-partner/includes/`：制作用PHPの共通部品。`inc_header.php`・`inc_sidebar.php`を置く
- `scripts/export-html.php`：制作用PHPから静的HTMLを書き出すPHP CLI専用スクリプト。PHPが動かない環境で見せる場合だけ使う（出力したHTMLはGit管理外）

Node.js環境ではnpmパッケージの`sass`を使用し、`node-sass`は使用しない。

| 編集元 | CSS出力先 |
|---|---|
| `shop-master/assets/scss/` | `shop-master/assets/css/` |
| `shop-partner/assets/scss/` | `shop-partner/assets/css/` |

- ディレクトリ単位で同名のCSSへ変換する。`_`で始まる共通部品は単独出力しない
- Client受注一覧の編集・制作確認は`shop-partner/orders.php`、固有スタイルは`shop-partner/assets/scss/order.scss`→`shop-partner/assets/css/order.css`とする。共通部分は`shop-partner/assets/scss/common.scss`→`shop-partner/assets/css/common.css`とし、`common.css`→`order.css`の順に読み込む。`_reset.scss`の読み込みは`common.scss`だけに置く
- Client商品一覧の編集・制作確認は`shop-partner/products.php`、固有スタイルは`shop-partner/assets/scss/products.scss`→`shop-partner/assets/css/products.css`とする。`common.css`→`products.css`の順に読み込み、JSは`common.js`だけを使用する
- 制作・修正・納品はPHPに一本化する。静的HTML（`shop-partner/orders.html`等）は常設せず、必要なときだけ`ddev exec php scripts/export-html.php`で書き出す。書き出したHTMLはGit管理外で、納品しない。SassのNode環境・npmコマンドは変更しない
- 現在のSCSSの記述構成を基準とし、共通レイアウト・ブランド設定は`common.scss`、受注一覧固有は`order.scss`、商品一覧固有は`products.scss`へ置く。既存のネストとセクションコメントを維持し、`admin.scss`への再編は前提にしない
- 色は既存の色変数・ブランド用CSSカスタムプロパティを使う。サイズは既存の`fz()`と流動フォント設定を使い、余白・幅・罫線などは`px`・`rem`・`em`の直接指定も認める。サイズの全面変数化や削除済み変数の復活は行わない
- class名は既存HTMLを優先し、役割が分かる名前にする。`.admin-*`／`.order-*`やBEMは必須にせず、要素セレクタと短いクラス名を使った現在のネスト構成を継続する
- 既存の関数・mixinを利用し、Codexは依頼なく新しいmixin・`@extend`・関数・パーシャルを追加したり、ファイルを再編したりしない。詳細は[実装連携ガイド](coding/IMPLEMENTATION_REFERENCE.md#クラス名とscssの書き方)を参照する
- 共通Sassの読み込み先は`--load-path=scss`で指定し、watch時も監視する
- `npm run sass`：通常コンパイル
- `npm run watch:sass`：変更監視・再コンパイル
- `npm run sass:prod`：圧縮コンパイル。ソースマップは生成しない
- `package.json`、`package-lock.json`、生成CSSはGit管理し、`node_modules/`と`*.map`は除外する

## 想定ユーザー

管理画面は、利用者と管理範囲が異なる2種類を用意する。

| 種別 | 呼称 | 主な対象 | 管理範囲 |
|---|---|---|---|
| マスター | マスター管理画面 | 運営側の管理者 | 全パートナーの店舗・商品・注文を横断して閲覧・操作し、顧客情報は閲覧のみ |
| クライアント | クライアント管理画面 | 代理店 | 所属パートナーの店舗・商品・注文だけを閲覧・操作し、顧客情報は所属パートナー内を閲覧のみ |

レイアウト、フォーム、ボタン、テーブル、タイポグラフィ、スペーシング、操作方法は共通化する。キーカラー、ロゴ、ナビゲーション、表示コンテンツ、操作権限は管理画面の種別によって変更できる。

2026-10-21確認。所属の検証はLaravelサーバー側で行う。初期権限はMaster／Clientの2区分とし、担当者ごとの「閲覧のみ／編集可能」等の細分化は設けない。各機能で認める操作は既存の業務仕様に従う。

### Client受注一覧の確定事項

- 発送状況の変更は一覧内で行い、注文単位で管理する。発送状況は選んだ時点で即時保存（非同期）とする（2026-10-19）。ステータス変更では注文者へメールを送らない。確認ダイアログは「キャンセル」選択時だけ挟む
- 一覧はページネーションを持ち、データなし・検索結果0件の表示を用意する。1ページは50件（まずはこの値で進める）、並び順は仮で新しい注文順。KPIの切り替え方式（リンク／JS）はバックエンド担当者が決める（2026-10-19）
- 入稿画像は注文者が注文時に添付し、注文内の商品明細ごとに紐づく。管理画面では確認・拡大表示・ダウンロードを行い、管理側の添付・差し替え・削除は行わない
- 入稿のある商品だけを表示し、どの商品にも入稿がない注文は入稿画像欄を出さない。注文側の形式・容量・受付件数の制限、拡大表示の方式、一括ダウンロードの要否、ファイル名の規則は未確定
- 展開行には、お客様が注文時に入力した備考（表示のみ）、入稿画像、キャンセル・返品の記録を表示する（2026-10-20）。店舗側の自由メモは当面設けない。キャンセル・返品の記録は、発送状況が「キャンセル」「返品対応」のときだけ表示し、注文単位の理由・対応メモ（任意）と全商品明細ごとの短いメモ（任意・2行程度・仮100文字）を1つの保存ボタンで保存する。ほかの状態に戻したときは隠すが、内容は消さない
- 注文単位で展開して確認する。閉じた状態でも、備考・入稿画像・キャンセル／返品の記録のいずれかがあることが分かるようにする。受注詳細画面や注文詳細リンクは設ける前提にせず、支払方法・配送希望日時など一覧にない情報の必要性と表示場所を確認する
- 発送状況の最終更新日時（日付・時刻）を表示し、変更が保存された時点で更新する。キャンセル・返品の記録の保存や入稿画像の確認・ダウンロードだけでは更新しない
- KPIは「すべて｜未着手｜発送待ち」とし、選択KPIと受注一覧の対象・件数を連動させる。初期選択は「すべて」。受付済みで準備・制作等の作業を始めていない注文を、受付日にかかわらず対象にする。「持ち越し」という日付の区分は設けない。対象ステータスとの対応・発送待ちの範囲等の詳細な集計条件は未確定
- 検索・詳細検索で受注を絞り込み、全件表示への切り替えはKPI「すべて」で行う。KPIと重複する範囲指定は設けない。検索条件とKPIの組み合わせや切り替え時の入力値保持は未確定
- 商品明細ごとに商品名・個数・税込の小計、注文単位で送料・合計（税込）を確認できるようにする。現行の集計行は送料と合計の2行。2026-10-20の決定により注文は店舗ごとに分け、「1注文＝送料1行＝発送状況1つ」を維持する。送料表・サイズ・温度帯・送料無料条件は下記「店舗と送料の確定事項」に従う。送料は標準税率10%・税込表示とし、計算・端数処理・税率ごとの内訳はバックエンドで決める。送料800円は表示例であり固定送料の決定ではない
- 注文日時は年月日と時刻（時・分）を表示する。一覧の住所はお届け先住所とする。顧客管理は注文者の情報を使う（[顧客管理の確定事項](#顧客管理の確定事項)を参照）。受注一覧の氏名・電話・メールの表示元、特に注文者メールかお届け先メールかは、顧客管理とは別に決める
- 画面固有の構成・見た目・寸法・操作・アクセシビリティと未確定事項は[Client受注一覧資料](design/CLIENT_ORDER_LIST.md)で管理する。Git除外の画像・生成記録はローカル補助資料とし、必須参照先にはしない

- 商品名の部分一致はDBの照合順序`utf8mb4_unicode_ci`に従い、英字の大文字・小文字、全角・半角、ひらがな・カタカナ、濁点・半濁点の有無、小さい文字を区別しない。「マグ」で「まぐ」、「ハン」で「パン」も一致する。取りこぼしを避けるため、この挙動を維持する（QA No.13の追記）
- 同じ条件のチェックが全部未選択の場合は、その条件を使わない。同じ条件内の複数選択はOR、キーワード・公開状態・在庫の状態・更新日の間はANDとする
- 在庫の状態は互いに重ならない区分とし、在庫を管理する商品は在庫切れ＝0、残りわずか＝1〜5、在庫あり＝6以上とする。「残りわずか」の基準値5は全商品共通で、一覧のラベル表示と検索の両方に使う
- 在庫管理なしの商品は、検索では「在庫あり」に含め、「残りわずか」「在庫切れ」には含めない。一覧の在庫数欄は「—」のままとする
- 更新日は片側指定可。開始日だけはその日以降、終了日だけはその日までとし、開始日・終了日の両日を含む。日付の判定は日本時間（`Asia/Tokyo`）で行う
- 更新日時の表示は日本時間とする
- 更新日の形式が正しくないときのエラー文は「日付を正しく入力してください」。開始日・終了日が逆転したときは「終了日は開始日以降の日付を指定してください」とする（QA No.12）
- 更新が新しい順で固定し、並び替え操作は置かない。1ページ50件。KPIは置かず、検索・フォーム・ボタン・空状態・ページ送りは受注一覧から共通化した部品を使う
- 通常・データなし・検索結果0件・更新日の逆転エラーを用意する。制作確認用の`preview`名は受注一覧と同じ`pager-middle`・`empty`・`no-results`・`date-error`とする

#### 商品画像の一時保存・保存時の扱い（2026-10-21確認）

以下は採用済みの仕様。一時保存にはLaravel標準の検証・ストレージ機能を使う。現行の制作用PHP・JS・画像の申し送りは保存時一括送信の旧実装で、次の作業で移行する（未対応）。

- 選択時に`images[]`を一時保存先へ送り、商品保存時は`image_order[]`に`existing:{ID}`／`temp:{一時画像ID}`を送る。ファイルは再送しない。有効な一時画像は入力エラー後も保持する
- 一時保存先は`storage/app/private/tmp/product-images/`（認可付きで表示）、本保存先は`storage/app/public/product-images/`（公開URLで表示）。XServer上でデモ・本番の保存領域を分ける。一時画像のユーザー・パス・期限はDBで管理する
- 一時画像の期限はアップロードから24時間、期限切れ画像の定期削除は1時間ごと。本保存済みの画像は対象外。期限切れ時は商品保存を止め、入力と有効な一時画像を保持し、該当画像の選び直しまたは取り消しを案内する
- アップロード中・失敗の状態を表示し、画像ごとに再試行・取り消しを用意する。アップロード中または失敗画像がある間は保存不可。形式・容量などの検証エラーは選び直しまたは取り消しで解消する
- 既存画像の削除は`image_delete[]`で送り、商品保存成功時に確定する。入力エラー時は削除予定を保持し、既存の実画像は残す。保存せず離れた場合は削除を確定しない
- 一時画像の取り消しは表示・保存対象から外し、即時削除通信はせず定期削除に任せる。APIのURL・応答形式、画像なし画像の具体的なファイル名・配置・対象画面、公開URLの接続、定期処理の実行方法、一時画像DBの詳細、トリミング・リサイズは未確定。[QA No.1](QA_BACKEND.md#no1-商品画像)を参照する

#### サイズごとのクール便欄の対象（2026-10-21、Kenの決定4）

サイズ別では、温度帯ごとに運送会社の規格を満たす荷物がそのサイズ区分に入りうる場合だけ、追加料金を設定対象にする。サイズSの1つ前の標準サイズをS_prev、その重量上限をW_prev、Sの重量上限をW_S、当該温度帯の3辺合計上限をC・重量上限をKとする。前のサイズは「店舗が使うサイズ」ではなく、運送会社の全標準サイズの直前を使う。

- 当該温度帯に非対応なら対象外。一番小さい標準サイズは、その温度帯に対応していれば対象
- それ以外は `min(S, C) > S_prev` または `min(W_S, K) > W_prev` なら対象
- ヤマトの140・160・180・200、ゆうパックの170は対象外。佐川の160とゆうパックの160は対象。実寸・重量・最長辺等の規格を広げるものではない
- サイズ共通の送料表は、運送会社が対応する温度帯を対象にする
- 対象外の欄は`disabled`＋`hidden`で送信せず、金額は画面内に保持する。画面での規格外表示は[店舗フォーム資料](design/CLIENT_STORE_FORM.md#配送送料の操作)を参照

### 集計の確定事項

2026-10-22のKenの決定。対象はClient（Masterは[画面一覧](#画面一覧)のとおり共通化候補）。

- 集計の軸は「何が・いつ・どれだけ売れたか」とする
- 期間の初期表示は今月。前月／翌月のボタンと月のセレクトで月を切り替える。それとは別に、期間を指定する欄を置く
- 翌月のボタンは、今月を表示しているときは押せない。月のセレクトの範囲は、最初の注文があった月から今月までとする
- 期間指定は開始日・終了日の両日を含み、日本時間（`Asia/Tokyo`）で判定する。[DB設計の「実装記録」](backend/DB_DESIGN.md#実装記録)では日時は日本時間で保存する方針。日付入力と逆転時のエラー文は、[Client商品一覧の更新日の検索](#client商品一覧の確定事項)と同じ部品・文言を使う
- 何日の売上とするかは、受注日（`orders.ordered_at`）で数える。今のDB設計に発送日・入金日を持つ列はなく、発送状況の最終更新日時である`shipping_status_updated_at`は発送日の代わりには使えない
- 商品ごとの表の上に、期間の売上の合計（商品代。送料を含めない）・販売個数の合計・注文件数の3つを表示する。送料の合計は表示しない
- 注文件数は店舗ごとの注文の数で数える（受注一覧の「1注文＝1店舗」と同じ）。キャンセル・返品は除く
- 商品ごとの表を置く。全商品を対象にし、ページ送りを付ける。上位N件だけの表示にはしない
- 商品ごとの表の列は、商品名・購入回数・販売個数・売上（税込）。売上は商品代だけで、送料を含めない。[DB設計の「注文・入稿」](backend/DB_DESIGN.md#注文入稿)では、`order_items.quantity`・`subtotal_incl_tax_yen`で販売個数・売上を集計できる設計
- 商品ごとの購入回数は、その商品を含む注文の数とする。1つの注文に同じ商品は1行なので、注文の分け方（店舗ごと／購入の単位）による差は出ない
- 商品は`order_items.product_id`でまとめ、表示する商品名は期間内の最新の注文時の名前（`order_items.product_name_snapshot`）とする
- 商品ごとの表の並び順は、初期は売上の多い順とし、販売個数の多い順に切り替えられる
- 発送状況が「キャンセル」「返品対応」の注文は、売上・販売個数・購入回数・合計に入れない。キャンセル件数・返品件数も別に表示しない。後日キャンセル・返品になった注文は、その受注日の期間の数字から抜け、過去の数字が変わることがある
- 今のDB設計ではキャンセル・返品は注文単位の発送状況だけで、商品明細ごとの一部返品や返金額は持たない。発送状況は元に戻せる（[Client受注一覧の確定事項](#client受注一覧の確定事項)）。画面の5つの選択肢は「新規受付／対応中／発送済／返品対応／キャンセル」（[Client受注一覧資料](design/CLIENT_ORDER_LIST.md#現行実装select-customer-statusへの統一2026-10-17)）。正式な呼称・選択肢は本資料の[未確定事項](#未確定事項)に残っている
- 店舗のセレクトを置き、初期値は「すべての店舗」とする。店舗が1つのパートナーでは出さない。`orders.store_id`で絞り込む。Masterでのパートナーの絞り込みは、Masterの画面を作るときに決める
- CSVは画面の合計と商品ごとの表を、選んだ期間・店舗の条件のまま出力する。注文者の氏名・連絡先などの個人情報は含めない
- 金額は税込で表示し、見出しや列名に「（税込）」と書く。税抜・税率ごとの内訳は出さない
- 売上の推移（グラフ・表）は最初は置かない。月別の推移（直近12か月など）は、使ってみて必要になったときに足す将来の候補とする
- 客単価は置かない
- 購入回数の数え方（店舗ごとの注文で数えるか、購入の単位で数えるか）は、商品ごとの表の論点から外す。顧客一覧の購入回数の論点として残る（[顧客管理の未確定事項](#顧客管理の未確定事項)）
- 顧客一覧・顧客詳細の購入回数・購入金額の合計も、集計と同じくキャンセル・返品の注文を含めない（2026-10-22、Kenの決定）。[顧客管理の確定事項](#顧客管理の確定事項)・[顧客一覧の画面資料](design/CLIENT_CUSTOMER_LIST.md)・[顧客詳細の画面資料](design/CLIENT_CUSTOMER_DETAIL.md)・両申し送りへ反映済み（2026-10-23）
