# ECサイト管理画面 仕様書

## 対象

ECサイト運用者が使用する管理画面。

Master / Clientの2種類を対象とする。画面一覧は以下に整理し、詳細な業務要件、項目、権限は確定した内容から順に追記する。

- プロジェクト名称（仮）：`熊日モール`

## 制作・実装方針

- デザイン実装プロジェクトは1つとし、Master / Clientの基本UIを共通化する
- 制作の流れ：Codexがプロンプトの依頼範囲で制作用PHP（HTML部分）・Sassを作成し、ユーザーが必要な箇所を調整し、Claudeが確認する。Codexは依頼範囲外のPHP・HTMLを作成・変更しない
- 静的HTML・Sassをブラウザで確認しながらデザインを固める
- 制作時はDDEVのPHPで共通ヘッダー・サイドバーをインクルードする。HTMLの組み立てにNodeは使わず、PHPは表示の共通化・現在地・静的出力時のリンク切り替えだけに限定する
- 制作用PHP（include構成）・Sass・生成CSSをバックエンド担当者へ渡し、Laravel・Bladeへの組み込みは担当者が行う。静的HTMLは納品物に含めない
- フロント（デザイン実装）の作業ではLaravelを構築しない。Laravelの構築・組み込みはバックエンド担当者が同じリポジトリで行う
- Figmaは必須工程ではなく、必要な場合のみ使用する
- Vite・Astroは現時点では使用しない

## プロジェクト範囲

- 静的HTML・Sassによる管理画面のデザイン実装と、共通UI・画面仕様・状態の整理を行う
- Codexは要件整理、仕様策定、依頼されたコードの提案・修正を支援する
- バックエンド処理、DB設計、API実装は対象外
- 依頼範囲外のPHP・HTMLを作成・変更しない

## フォルダとSass

- ルートの `index.html` は制作確認用のページ一覧で、納品しない。画面の追加や状態の変更のたびに更新する
- `scss/`：`@use`で読み込むreset・変数・既存の関数やmixinなど。単独のCSS出力対象にしない
- `shop-master/`：Master用の静的HTMLとアセット。対象URLは`https://shop-master.kumanichi.com/`
- `shop-partner/`：Client用の静的HTMLとアセット。対象URLは`https://shop-partner.kumanichi.com/`
- `docs/`：仕様・デザイン方針・実装引き渡し資料
- `.agents/`：プロジェクト専用スキル
- `backend/`：バックエンド（Laravel）のコード。バックエンド担当者が使う
- `shop-partner/includes/`：制作用PHPの共通部品。`inc_header.php`・`inc_sidebar.php`を置く
- `scripts/export-html.php`：制作用PHPから静的HTMLを書き出すPHP CLI専用スクリプト。PHPが動かない環境で見せる場合だけ使う（出力したHTMLはGit管理外）

Node.js環境ではnpmパッケージの`sass`を使用し、`node-sass`は使用しない。

| 編集元 | CSS出力先 |
|---|---|
| `shop-master/assets/scss/` | `shop-master/assets/css/` |
| `shop-partner/assets/scss/` | `shop-partner/assets/css/` |

- ディレクトリ単位で同名のCSSへ変換する。`_`で始まる共通部品は単独出力しない
- Client受注一覧の編集・制作確認は`shop-partner/orders.php`、固有スタイルは`shop-partner/assets/scss/order.scss`→`shop-partner/assets/css/order.css`とする。共通部分は`shop-partner/assets/scss/common.scss`→`shop-partner/assets/css/common.css`とし、`common.css`→`order.css`の順に読み込む。`_reset.scss`の読み込みは`common.scss`だけに置く
- Client商品一覧の編集・制作確認は`shop-partner/products.php`、固有スタイルは`shop-partner/assets/scss/products.scss`→`shop-partner/assets/css/products.css`とする。`common.css`→`products.css`の順に読み込み、JSは`common.js`だけを使用する
- 制作・修正・納品はPHPに一本化する。静的HTML（`shop-partner/orders.html`等）は常設せず、必要なときだけ`ddev exec php scripts/export-html.php`で書き出す。書き出したHTMLはGit管理外で、納品しない。SassのNode環境・npmコマンドは変更しない
- 現在のSCSSの記述構成を基準とし、共通レイアウト・ブランド設定は`common.scss`、受注一覧固有は`order.scss`、商品一覧固有は`products.scss`へ置く。既存のネストとセクションコメントを維持し、`admin.scss`への再編は前提にしない
- 色は既存の色変数・ブランド用CSSカスタムプロパティを使う。サイズは既存の`fz()`と流動フォント設定を使い、余白・幅・罫線などは`px`・`rem`・`em`の直接指定も認める。サイズの全面変数化や削除済み変数の復活は行わない
- class名は既存HTMLを優先し、役割が分かる名前にする。`.admin-*`／`.order-*`やBEMは必須にせず、要素セレクタと短いクラス名を使った現在のネスト構成を継続する
- 既存の関数・mixinを利用し、Codexは依頼なく新しいmixin・`@extend`・関数・パーシャルを追加したり、ファイルを再編したりしない。詳細は[実装連携ガイド](coding/IMPLEMENTATION_REFERENCE.md#クラス名とscssの書き方)を参照する
- 共通Sassの読み込み先は`--load-path=scss`で指定し、watch時も監視する
- `npm run sass`：通常コンパイル
- `npm run watch:sass`：変更監視・再コンパイル
- `npm run sass:prod`：圧縮コンパイル。ソースマップは生成しない
- `package.json`、`package-lock.json`、生成CSSはGit管理し、`node_modules/`と`*.map`は除外する

### Client受注一覧の確定事項

- 発送状況の変更は一覧内で行い、注文単位で管理する。発送状況は選んだ時点で即時保存（非同期）とする（2026-10-19）。ステータス変更では注文者へメールを送らない。確認ダイアログは「キャンセル」選択時だけ挟む
- 一覧はページネーションを持ち、データなし・検索結果0件の表示を用意する。1ページは50件（まずはこの値で進める）、並び順は仮で新しい注文順。KPIの切り替え方式（リンク／JS）はバックエンド担当者が決める（2026-10-19）
- 入稿画像は注文者が注文時に添付し、注文内の商品明細ごとに紐づく。管理画面では確認・拡大表示・ダウンロードを行い、管理側の添付・差し替え・削除は行わない
- 入稿のある商品だけを表示し、どの商品にも入稿がない注文は入稿画像欄を出さない。注文側の形式・容量・受付件数の制限、拡大表示の方式、一括ダウンロードの要否、ファイル名の規則は未確定
- 展開行には、お客様が注文時に入力した備考（表示のみ）、入稿画像、キャンセル・返品の記録を表示する（2026-10-20）。店舗側の自由メモは当面設けない。キャンセル・返品の記録は、発送状況が「キャンセル」「返品対応」のときだけ表示し、注文単位の理由・対応メモ（任意）と全商品明細ごとの短いメモ（任意・2行程度・仮100文字）を1つの保存ボタンで保存する。ほかの状態に戻したときは隠すが、内容は消さない
- 注文単位で展開して確認する。閉じた状態でも、備考・入稿画像・キャンセル／返品の記録のいずれかがあることが分かるようにする。受注詳細画面や注文詳細リンクは設ける前提にせず、支払方法・配送希望日時など一覧にない情報の必要性と表示場所を確認する
- 発送状況の最終更新日時（日付・時刻）を表示し、変更が保存された時点で更新する。キャンセル・返品の記録の保存や入稿画像の確認・ダウンロードだけでは更新しない
- KPIは「すべて｜未着手｜発送待ち」とし、選択KPIと受注一覧の対象・件数を連動させる。初期選択は「すべて」。受付済みで準備・制作等の作業を始めていない注文を、受付日にかかわらず対象にする。「持ち越し」という日付の区分は設けない。対象ステータスとの対応・発送待ちの範囲等の詳細な集計条件は未確定
- 検索・詳細検索で受注を絞り込み、全件表示への切り替えはKPI「すべて」で行う。KPIと重複する範囲指定は設けない。検索条件とKPIの組み合わせや切り替え時の入力値保持は未確定
- 商品明細ごとに商品名・個数・税込の小計、注文単位で送料・合計（税込）を確認できるようにする。現行の集計行は送料と合計の2行。2026-10-20の決定により注文は店舗ごとに分け、「1注文＝送料1行＝発送状況1つ」を維持する。送料表・サイズ・温度帯・送料無料条件は下記「店舗と送料の確定事項」に従う。送料は標準税率10%・税込表示とし、計算・端数処理・税率ごとの内訳はバックエンドで決める。送料800円は表示例であり固定送料の決定ではない
- 注文日時は年月日と時刻（時・分）を表示する。一覧の住所はお届け先住所とする。氏名・電話・メールの参照元、特に注文者メールかお届け先メールかは別途確認する
- 画面固有の構成・見た目・寸法・操作・アクセシビリティと未確定事項は[Client受注一覧資料](design/CLIENT_ORDER_LIST.md)で管理する。Git除外の画像・生成記録はローカル補助資料とし、必須参照先にはしない

### Client商品一覧の確定事項

2026-10-19のKenの決定。詳細な構成・操作・見た目の案・実装メモは[Client商品一覧資料](design/CLIENT_PRODUCT_LIST.md)を参照する。同日に制作用PHP・Sass・生成CSSを作成し、公開バッジと在庫・日時の2行表示の決定を反映済み。残りの見た目は調整中。JSは既存の共通JSだけを使用し、業務処理は実装していない。

- ページ見出しは「商品一覧」だけとし、受注一覧のような日付は出さない（Kenの決定、2026-10-19）
- 規格（サイズ・色など）と商品コードはいったん設けない。1商品1行の`table`とし、列は「ID｜画像｜商品名｜価格｜在庫数｜公開状態｜更新日時｜編集」。価格は税込、画像は販売用の商品画像。更新日時は日付・時刻を2行に分け、右揃え・`tabular-nums`。1つの`time`・`datetime`の中を2つの`span`に分ける
- 画像がない商品は、画像の位置に代わりの表示を置き、画像がないことが文字でも伝わるようにする。具体的な見た目は未確定
- 公開状態は公開／非公開の表示のみ。安全のため切り替えは商品詳細で行い、編集アイコンから共通フォームの編集状態へ遷移する。フォームではラジオで選び、保存と同時に反映する（2026-10-20）。入稿の有無も商品詳細のチェックボックス「入稿あり」で設定・確認し、一覧には出さない。詳細は[Client商品詳細（登録・編集）資料](design/CLIENT_PRODUCT_FORM.md)を参照
- 公開状態は角の丸い塗りのバッジ（公開＝青`#3A5F95`・非公開＝グレー`#6B7079`、白文字・500、幅5em・中央ぞろえ、枠・点なし）。非公開バッジは`opacity: 0.7`で実表示約2.8:1となるが、「非公開を控えめに見せる」ため白文字4.5:1の決まりの例外とする（Kenの決定、2026-10-19）。ホバーでも色・カーソルを変えず、行全体は薄くしない。編集アイコンはホバーで1pxの`$color-border-card`枠と文字・背景・枠色のtransitionを付ける。詳細は画面資料・`DESIGN_TOKENS.md`を参照
- キーワードは商品名・ID。詳細検索は公開状態・在庫の状態（在庫あり／残りわずか／在庫切れ）のチェックボックスと更新日の期間。在庫切れ0・残りわずかのラベルは数字の下の行へ右揃えで置き、ラベル有無で数字の右端をずらさない（Kenの決定、2026-10-19）。ラベルの文字サイズ・補助色は維持。残りわずかの基準値は未確定
- 在庫管理なしの商品は、在庫数を「—」＋読み上げ用「在庫管理なし」（`.sr-only`）で表示し、「在庫切れ」「残りわずか」の対象にしない（2026-10-20、Kenの決定）。在庫検索での扱いは未確定。既存PHPへの表示例の追加は今回の対象外
- 更新が新しい順で固定し、並び替え操作は置かない。1ページ50件。KPIは置かず、検索・フォーム・ボタン・空状態・ページ送りは受注一覧から共通化した部品を使う
- 通常・データなし・検索結果0件・更新日の逆転エラーを用意する。制作確認用の`preview`名は受注一覧と同じ`pager-middle`・`empty`・`no-results`・`date-error`とする

### Client商品詳細（登録・編集）の確定事項

2026-10-20のKenの決定。制作1回目としてPHP・Sassで骨組みと主な状態を作成済み。現在は完成（引き渡し前）で、[商品フォームの申し送り](coding/HANDOFF_CLIENT_PRODUCT_FORM.md)を作成済み。2-Aで自動判定・食品開閉・在庫連動・クール便注意を実装。2-Bで画像操作・送信制御・自動フォーカス・離脱警告を実装済み。以下以外の見た目・入力条件を確定扱いにせず、案と詳細は[Client商品詳細（登録・編集）資料](design/CLIENT_PRODUCT_FORM.md)を参照する。

- 商品詳細と商品登録は1つのフォームで作る。新規／編集の違いは画面資料の表で管理する。編集時は配送温度帯を含め、保存済みの値を各欄に表示する
- レイアウトは1列で箱を縦に並べ、順番は「基本情報 → 商品画像 → 価格・在庫 → 配送 → 注文者からのデータ入稿 → 商品仕様（食品表示）→ 公開設定」
- 保存バーはメイン領域内に置き、`position: sticky; bottom: 0`で画面下に固定する。サイドバーの開閉・重ね表示と干渉させないため`fixed`は使わない
- カテゴリ・規格は最初は使わず、空の欄は置かない。カテゴリは将来、基本情報に追加する想定。価格・在庫は独立した1つの箱にし、規格追加時に箱ごと規格の表へ差し替えられる構成とする
- 価格は税込で入力・表示する。税抜・税額の計算と端数処理はバックエンドで行う。具体的な計算・端数処理の方式は今回決めていない
- 商品名・価格（税込）・消費税率は必須とする（Kenの決定、2026-10-20）
- 「在庫を管理しない」は、在庫数を持たずにいつでも販売できる商品（受注生産・名入れなど）のための設定とする。チェック時は在庫数欄を無効にする（2026-10-20、Kenの決定）。チェック連動のJSは2-Aで実装済み（値は保持）
- 入稿はチェックボックス「入稿あり」1つ（`name="upload" value="1"`）とし、ラジオとlegend「入稿の有無」は使わない。下に補助文「注文者から画像を受け付ける場合はチェックしてください」を置き、`aria-describedby`で関連付ける。制作例は全10状態でチェックなし。編集の実データでは保存済みの値を表示する
- 商品は店舗に紐付けて登録する。基本情報の箱に必須の「店舗」セレクトを置く。店舗が1つの場合に自動選択するのは案
- 「配送」の箱を設け、配送温度帯を食品の箱から移す。ラジオ「常温・冷蔵・冷凍」、必須、新規の初期値は常温。食品のオン・オフにかかわらず入力・保存する。配送用のサイズ区分は、将来候補の商品規格（サイズ・色等）とは別の項目
- 配送サイズのセレクトは廃止し、配送の箱で梱包時の縦・横・高さ（cm）・重さ（kg）を入力する（2026-10-20、Kenの決定）。選んだ店舗が使うサイズのうち、3辺合計と運送会社の規格の重さ上限の両方に収まる一番小さいサイズを自動判定する。「その他」の独自規格は後回しとし、初期対象に含めない。上限ちょうどを含める比較条件は未確定事項に残す
