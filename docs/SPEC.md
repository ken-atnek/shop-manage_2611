# ECサイト管理画面 仕様書

## 対象

ECサイト運用者が使用する管理画面。

Master / Clientの2種類を対象とする。画面一覧は以下に整理し、詳細な業務要件、項目、権限は確定した内容から順に追記する。

- プロジェクト名称（仮）：`熊日モール`

## 制作・実装方針

- デザイン実装プロジェクトは1つとし、Master / Clientの基本UIを共通化する
- HTMLはユーザーが手打ちし、Codexは依頼なくHTMLを自動生成・書き出ししない
- 静的HTML・Sassをブラウザで確認しながらデザインを固める
- 静的HTML・Sass・生成CSSをバックエンド担当者へ渡し、Laravel・Bladeへの組み込みは担当者が行う
- このプロジェクトではLaravelを構築しない
- Figmaは必須工程ではなく、必要な場合のみ使用する
- Vite・Astroは現時点では使用しない

## プロジェクト範囲

- 静的HTML・Sassによる管理画面のデザイン実装と、共通UI・画面仕様・状態の整理を行う
- Codexは要件整理、仕様策定、依頼されたコードの提案・修正を支援する
- バックエンド処理、DB設計、API実装は対象外
- 依頼なくHTMLを自動生成・書き出ししない

## フォルダとSass

- `scss/`：`@use`で読み込むreset・変数・既存の関数やmixinなど。単独のCSS出力対象にしない
- `shop-master/`：Master用の静的HTMLとアセット。対象URLは`https://shop-master.kumanichi.com/`
- `shop-partner/`：Client用の静的HTMLとアセット。対象URLは`https://shop-partner.kumanichi.com/`
- `docs/`：仕様・デザイン方針・実装引き渡し資料
- `.agents/`：プロジェクト専用スキル

Node.js環境ではnpmパッケージの`sass`を使用し、`node-sass`は使用しない。

| 編集元 | CSS出力先 |
|---|---|
| `shop-master/assets/scss/` | `shop-master/assets/css/` |
| `shop-partner/assets/scss/` | `shop-partner/assets/css/` |

- ディレクトリ単位で同名のCSSへ変換する。`_`で始まる共通部品は単独出力しない
- Client受注一覧固有のスタイルは、`shop-partner/orders.html` ↔ `shop-partner/assets/scss/order.scss`の1対1で作り、`shop-partner/assets/css/order.css`へ出力する。共通部分はユーザーが独立させた`shop-partner/assets/scss/common.scss`から`shop-partner/assets/css/common.css`へ出力し、`orders.html`は`common.css`→`order.css`の順に読み込む。`_reset.scss`の読み込みは`common.scss`だけに置く
- 現在のSCSSの記述構成を基準とし、共通レイアウト・ブランド設定は`common.scss`、受注一覧固有は`order.scss`へ置く。既存のネストとセクションコメントを維持し、`admin.scss`への再編は前提にしない
- 色は既存の色変数・ブランド用CSSカスタムプロパティを使う。サイズは既存の`fz()`と流動フォント設定を使い、余白・幅・罫線などは`px`・`rem`・`em`の直接指定も認める。サイズの全面変数化や削除済み変数の復活は行わない
- class名は既存HTMLを優先し、役割が分かる名前にする。`.admin-*`／`.order-*`やBEMは必須にせず、要素セレクタと短いクラス名を使った現在のネスト構成を継続する
- 既存の関数・mixinを利用し、Codexは依頼なく新しいmixin・`@extend`・関数・パーシャルを追加したり、ファイルを再編したりしない。詳細は[実装連携ガイド](coding/IMPLEMENTATION_REFERENCE.md#クラス名とscssの書き方)を参照する
- 共通Sassの読み込み先は`--load-path=scss`で指定し、watch時も監視する
- `npm run sass`：通常コンパイル
- `npm run watch:sass`：変更監視・再コンパイル
- `npm run sass:prod`：圧縮コンパイル。ソースマップは生成しない
- `package.json`、`package-lock.json`、生成CSSはGit管理し、`node_modules/`と`*.map`は除外する

### Client受注一覧の確定事項

- 発送状況の変更とメモ編集は一覧内で行い、発送状況と全体メモは注文単位で管理する。保存方法は未確定
- 入稿画像は注文者が注文時に添付し、注文内の商品明細ごとに紐づく。管理画面では確認・拡大表示・ダウンロードを行い、管理側の添付・差し替え・削除は行わない
- 入稿のある商品だけを表示し、どの商品にも入稿がない注文は入稿画像欄を出さない。注文側の形式・容量・受付件数の制限、拡大表示の方式、一括ダウンロードの要否、ファイル名の規則は未確定
- 注文単位でメモ・入稿画像を展開して確認する。閉じた状態でも、メモまたは入稿画像の有無が分かるようにする。受注詳細画面や注文詳細リンクは設ける前提にせず、支払方法・配送希望日時など一覧にない情報の必要性と表示場所を確認する
- 発送状況の最終更新日時（日付・時刻）を表示し、変更が保存された時点で更新する。メモ編集・入稿画像の確認やダウンロードだけでは更新しない
- KPIは「すべて｜本日の新規｜持ち越し｜発送待ち」とし、選択KPIと受注一覧の対象・件数を連動させる。「すべて」は全件表示、「持ち越し」は前日以前に受け付けて未対応の注文を表す。KPIの詳細な集計条件は未確定
- 検索・詳細検索で受注を絞り込み、全件表示への切り替えはKPI「すべて」で行う。KPIと重複する範囲指定は設けない。検索条件とKPIの組み合わせや切り替え時の入力値保持は未確定
- 商品明細ごとに商品名・個数・税込の小計、注文単位で送料・合計（税込）を確認できるようにする。現行の集計行は送料と合計の2行とし、送料の計算方法・送料無料の条件・消費税の表示要否・端数処理は未確定。送料800円は表示例であり固定送料の決定ではない
- 注文日は年月日表記。一覧の住所はお届け先住所とする。氏名・電話・メールの参照元、特に注文者メールかお届け先メールかは別途確認する
- 画面固有の構成・見た目・寸法・操作・アクセシビリティと未確定事項は[Client受注一覧資料](design/CLIENT_ORDER_LIST.md)で管理する。Git除外の画像・生成記録はローカル補助資料とし、必須参照先にはしない

### Masterへの展開方針

- Clientと同じ目的・操作の画面は、共通レイアウトと共通コンポーネントを利用する
- Master側へ必要な画面だけを採用し、同じ画面を別設計で作り直さない
- Masterでは、全クライアント横断表示と特定クライアント表示のどちらが必要かを画面ごとに確認する
- Master専用の権限・操作・項目が必要な場合は、共通画面との差分として管理する
- Master側に採用する画面と管理範囲は未確定

### 制作順

- 管理画面本体を先に作成し、共通の配色、フォーム、ボタンが確定してからログインページを作成する
- ログインページは制作順の最後とする
- ログインUIはMaster / Clientで可能な限り共通化し、入口や認証方法の違いが判明した場合のみ差分を設ける

- ヘッダーの有無と表示内容
- サイドバーの有無、幅、開閉仕様
- パンくず・ページタイトル・補助説明

- PC・タブレットの具体的な対応幅とタブレットの向き

### 管理画面種別による違い

次の項目は共通仕様とせず、マスター／クライアントごとの差分として管理できるようにする。

- ブランドカラー・アクセントカラー
- ロゴ、サービス名、管理画面名
- サイドバーのメニュー項目
- ダッシュボードや各画面の表示コンテンツ
- 閲覧・登録・編集・削除などの操作権限
- 注意文、補助説明、問い合わせ先

同じ意味と機能を持つUIは、管理画面種別が異なっても配置、サイズ、状態、操作方法を揃える。

## 共通UI

各画面で必要性を確認し、確定後に共通仕様へ追加する。

フォーム部品は画面ごとに個別作成せず、最初に必要になった時点で共通仕様を決める。確定済みの部品は、特別な理由がない限り全画面で同じ仕様を使用する。

- ボタン
- テキスト入力、セレクト、チェックボックス、ラジオボタン
- 検索・絞り込み・並び替え
- テーブル、ページネーション
- タブ、ドロワー、モーダル
- アラート、トースト、バリデーション
- 空状態、読み込み中、エラー状態

### フォーム部品の共通化

対象：

- テキスト入力
- セレクト
- テキストエリア
- チェックボックス
- ラジオボタン
- 日付入力
- ファイル選択

部品ごとに次を定義する。

- サイズと高さ
- ラベル、必須・任意表示
- プレースホルダーと初期値
- 補助説明と文字数表示
- Default / Hover / Focus / Filled / Disabled / Read only / Error
- エラー文の位置と表示方法
- 前後に配置するアイコンや単位表記
- 横幅、最小幅、長文時の挙動

新しい画面で既存仕様に合わないケースが出た場合は、その画面専用の部品を増やす前に共通仕様の拡張で対応できるか確認する。

## 操作と状態

各機能について最低限、次を定義する。

- 初期表示
- 入力中・選択中
- 保存前・保存中・保存完了
- バリデーションエラー
- 通信エラー
- データなし
- 権限不足・操作不可
- 削除など不可逆操作の確認

## デザイン方針

- 業務画面として情報の読み取りやすさと操作の明確さを優先する
- 装飾より、階層・余白・ラベル・状態差で整理する
- 同じ意味の操作と状態は全画面で統一する
- デザイントークンは`DESIGN_TOKENS.md`を参照する
- 案件固有の方向性は`docs/design/DESIGN.md`へ記載する

## アクセシビリティ

- 文字と背景のコントラストを確保する
- 色だけで状態を伝えない
- フォーカス状態を用意する
- フォームはラベル、説明、エラーの関係が分かる構造にする
- 操作対象は十分なクリック・タップ領域を確保する
