## 想定ユーザー

管理画面は、利用者と管理範囲が異なる2種類を用意する。

| 種別 | 呼称 | 主な対象 | 管理範囲 |
|---|---|---|---|
| マスター | マスター管理画面 | 運営側の管理者 | 未確定 |
| クライアント | クライアント管理画面 | 代理店 | 未確定 |

基本的なUI、フォーム部品、レイアウト規則は共通化する。色、ナビゲーション、表示コンテンツ、利用可能な操作は、管理画面の種別によって異なる場合がある。

担当者単位の権限分けが必要かは未確定。

### Masterへの展開方針

- Clientと同じ目的・操作の画面は、共通レイアウトと共通コンポーネントを利用する
- Master側へ必要な画面だけを採用し、同じ画面を別設計で作り直さない
- Masterでは、全クライアント横断表示と特定クライアント表示のどちらが必要かを画面ごとに確認する
- Master専用の権限・操作・項目が必要な場合は、共通画面との差分として管理する
- Master側に採用する画面と管理範囲は未確定

### 制作順

- 管理画面本体を先に作成し、共通の配色、フォーム、ボタンが確定してからログインページを作成する
- ログインページは制作順の最後とする
- ログインUIはMaster / Clientで可能な限り共通化し、入口や認証方法の違いが判明した場合のみ差分を設ける

### 管理画面種別による違い

次の項目は共通仕様とせず、マスター／クライアントごとの差分として管理できるようにする。

- ブランドカラー・アクセントカラー
- ロゴ、サービス名、管理画面名
- サイドバーのメニュー項目
- ダッシュボードや各画面の表示コンテンツ
- 閲覧・登録・編集・削除などの操作権限
- 注意文、補助説明、問い合わせ先

同じ意味と機能を持つUIは、管理画面種別が異なっても配置、サイズ、状態、操作方法を揃える。

## 共通UI

各画面で必要性を確認し、確定後に共通仕様へ追加する。

フォーム部品は画面ごとに個別作成せず、最初に必要になった時点で共通仕様を決める。確定済みの部品は、特別な理由がない限り全画面で同じ仕様を使用する。

- ボタン
- テキスト入力、セレクト、チェックボックス、ラジオボタン
- 検索・絞り込み・並び替え
- テーブル、ページネーション
- タブ、ドロワー、モーダル
- アラート、トースト、バリデーション
- 空状態、読み込み中、エラー状態

### フォーム部品の共通化

対象：

- テキスト入力
- セレクト
- テキストエリア
- チェックボックス
- ラジオボタン
- 日付入力
- ファイル選択

部品ごとに次を定義する。

- サイズと高さ
- ラベル、必須・任意表示
- プレースホルダーと初期値
- 補助説明と文字数表示
- Default / Hover / Focus / Filled / Disabled / Read only / Error
- エラー文の位置と表示方法
- 前後に配置するアイコンや単位表記
- 横幅、最小幅、長文時の挙動

新しい画面で既存仕様に合わないケースが出た場合は、その画面専用の部品を増やす前に共通仕様の拡張で対応できるか確認する。

## 操作と状態

各機能について最低限、次を定義する。

- 初期表示
- 入力中・選択中
- 保存前・保存中・保存完了
- バリデーションエラー
- 通信エラー
- データなし
- 権限不足・操作不可
- 削除など不可逆操作の確認

## デザイン方針

- 業務画面として情報の読み取りやすさと操作の明確さを優先する
- 装飾より、階層・余白・ラベル・状態差で整理する
- 同じ意味の操作と状態は全画面で統一する
- デザイントークンは`DESIGN_TOKENS.md`を参照する
- 案件固有の方向性は`docs/design/DESIGN.md`へ記載する

## アクセシビリティ

- 文字と背景のコントラストを確保する
- 色だけで状態を伝えない
- フォーカス状態を用意する
- フォームはラベル、説明、エラーの関係が分かる構造にする
- 操作対象は十分なクリック・タップ領域を確保する
