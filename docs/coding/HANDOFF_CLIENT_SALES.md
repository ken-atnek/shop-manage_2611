- 作成日：2026-10-22

- 作成：フロント（Ken・Codex）

共通の内容は[HANDOFF_CLIENT_COMMON.md](HANDOFF_CLIENT_COMMON.md)を参照。ここには集計固有の内容だけを記載する。仕様の正は[SPECの集計の確定事項](../SPEC.md#集計の確定事項)と[集計の画面資料](../design/CLIENT_SALES.md)。食い違う場合は仕様資料を優先し、フロントへ知らせてほしい。

## 1. 制作用PHPのうち、Bladeへ移さないもの

共通レイアウト・静的出力の扱いは[共通申し送り§1](HANDOFF_CLIENT_COMMON.md#1-共通レイアウトと制作専用の仕組み)を参照。

| 対象 | 内容 | Bladeでの扱い |
|---|---|---|
| `$previewState`（`?preview=`）と各`$is…State` | `empty`・`pager-middle`・`date-error`・`error`・`single-store`・`date-range`・`first-month`の制作確認用分岐 | 移さず、実データ・適用条件・検証結果・取得結果で分岐する |
| `$selectedMonth`・`$periodFrom`・`$periodTo`・`$periodLabel`・`$monthHelp` | 今日＝2026-10-22、今月＝2026年10月、最初の注文月＝2026年1月の固定例。期間指定・逆転エラーの日付も表示例 | 実際の今日・最初の注文月・適用済み期間・入力値から生成する |
| `$totalAmount`・`$totalQuantity`・`$totalOrders` | 合計¥1,284,560・1,932個・418件（空状態は0） | 選択中の期間・店舗全体の実際の集計値へ置き換える |
| `$salesProducts`・`$rangeLabel`・ページ番号 | 架空の商品10行を抜粋。全426商品・1ページ50件・全9ページ。通常1〜50件／1ページ目、途中201〜250件／5ページ目でも同じ10行 | 実データのループ・全件数・表示範囲・ページ数に置き換える。10行に制限する仕様ではない |
| `$storeValue`・`$storeLabel`・店舗の選択肢 | 架空の3店舗・ID、単一店舗の表示例 | 所属パートナーの実際の店舗に置き換える |
| `$appliedConditions`・`$pagerQuery`・フォームのhidden・リンク | 適用済み条件の保持を示す例。並び順は`sales`に固定され、実際のGET値では切り替わらない | 実際の適用済み条件から生成する。入力中の日付と区別し、並び順の選択値・captionも同期する |
| `$staticExport`・`$pageExtension`・`$salesPath`・`$currentPage = 'sales'` | 静的出力の拡張子切り替えとサイドバーの現在地 | 本番ルート・現在地判定に置き換え、「集計」の`aria-current="page"`を維持する |

集計・日付判定・CSV生成・並び替え・実際のページ切り替えは制作用PHPに実装していない。送信後も固定表示例へ戻るため、その挙動を本番仕様として移さない。

## 2. 画面の構成

B案の構成は確定（2026-10-22、Kenの決定）。共通ヘッダー・サイドバーの中の`main.admin-main.sales-page`に、次の順で置く。

| 順 | 領域 | 主なclass・idと構造 |
|---|---|---|
| 1 | ページ見出し | `.page-heading`内の`h1`「集計」 |
| 2 | 期間の操作 | `.sales-period`（`aria-label="集計期間"`）内の`.period-fields`に`.month-form`と`.period-form`。月は`.month-controls`・`.month-button`・`#sales-month`、期間は`fieldset`・`legend`・`.date-range`・`#sales-from`・`#sales-to`・`.period-submit`。下に`.applied-period`と必要な場合だけ`#sales-month-help.period-help` |
| 3 | 店舗・CSV | `.sales-toolbar`に`.store-form`・`#sales-store`と`.csv-form`・`.csv-download`。単一店舗は`.sales-store-name` |
| 4 | 合計3つ | `.sales-summary`内の`dl.sales-totals`で`dt`と`dd`を対応させる。注記は`.sales-note`。表示専用で操作は付けない |
| 5 | 商品ごとの表 | `.sales-results`（`aria-labelledby="sales-list-heading"`）。`.list-heading.sales-list-heading`に`.sales-list-title`・`h2#sales-list-heading`「商品ごとの売上」・`.count`、右上に`.sort-form`・`#sales-sort`。その下の`.sales-scroll`に`table.sales-table` |
| 6 | ページ送り | `nav.pagination`（`aria-label="商品別集計のページ"`）・`.pagination-list`・`.page-status` |

- 月の操作と期間指定欄は常時表示する。1行に収まらない幅では2段に折り返す。月と期間の間の区切り線・開閉操作は置かない。開始日〜終了日と集計ボタンのまとまり自体が収まらない場合はページ全体で横スクロールする
- `.sales-scroll`だけを独立したスクロール領域にしない。スクロールの基本形は共通申し送り§1に従う
- `.sales-list-title`の`aria-live="polite" aria-atomic="true"`、各セレクト・日付欄の可視labelと`for`／`id`の対応を維持する
- 表は`caption.sr-only`に適用期間・店舗・並び順を出力し、列見出しは`th scope="col"`を維持する。列見出しは表示だけで、並び替えボタンや`aria-sort`は付けない

## 3. 表示の決まり（集計条件）

業務仕様の正は[SPECの集計の確定事項](../SPEC.md#集計の確定事項)。次の条件で合計と商品表をそろえる。

- 受注日（`orders.ordered_at`）で集計し、日本時間（`Asia/Tokyo`）で期間を判定する。発送状況の最終更新日時`shipping_status_updated_at`を発送日の代わりに使わない
- 売上は商品代（税込）だけで、送料を含めない。商品明細の`order_items.quantity`・`subtotal_incl_tax_yen`が販売個数・売上の集計対象となる
- 発送状況が「キャンセル」「返品対応」の注文は、売上・販売個数・購入回数・合計に含めない。キャンセル件数・返品件数も出さない。後日のキャンセル・返品で受注日の期間の数字が変わり得る。判定に使う保存値は§9で決めてほしい
- 注文件数は店舗ごとの注文数（1注文＝1店舗）。商品ごとの購入回数は、その商品を含む注文数とする
- 商品は`order_items.product_id`でまとめ、期間内の最新の注文時の商品名（`order_items.product_name_snapshot`）を表示する。現在の商品名へ置き換えない
- 合計3つは、表の現在ページの小計ではなく、選択中の期間・店舗全体の値とする
- 税込表記のみ。見出し・列名に「（税込）」を付け、送料合計・税抜・税率別内訳・売上推移のグラフや表・客単価は出さない
- 画面の注記は「売上は商品代（税込）の合計です。送料、キャンセル・返品の注文は含みません。」（`.sales-note`）を維持する

| 対象 | class | 書式 |
|---|---|---|
| 売上の合計（税込） | `.sales-totals`内の`dd` | `¥`＋3桁区切り（例：`¥1,284,560`、0は`¥0`）。「円」は重ねない |
| 販売個数の合計・注文件数 | `.sales-totals`内の`dd`・`.unit` | 3桁区切り＋「個」／「件」（例：`1,932個`・`418件`、0は`0個`・`0件`） |
| 商品名 | `.sales-product` | 左揃え。長い名前も全文を折り返し、行数制限で省略しない。画像・詳細リンクは現状付けていない（未確定） |
| 購入回数 | `.sales-count` | 3桁区切り＋「回」 |
| 販売個数 | `.sales-quantity` | 3桁区切り＋「個」 |
| 売上（税込） | `.sales-amount`・見出し内の`.tax-note` | `¥`＋3桁区切り。「（税込）」をまとまりとして扱う |

合計の数値と表の数値3列は右揃え・`tabular-nums`。数値と単位を離して折り返さない。書式・揃えは現行Sassの表示であり、合計の箱の寸法等の最終調整は画面資料に残る。

## 4. 期間の決まり

- 初期表示は今月。`.applied-period`に適用済み期間を表示し、今月は「（今日まで）」を付ける（制作例：`2026/10/01〜2026/10/22（今日まで）`）
- 月のセレクトは最初の注文月〜今月。今月では翌月ボタンを無効にし、先の月は選べない。制作では`button type="button" disabled`を使い、実行・Tab停止を防ぐ
- 最初の注文月で前月を`disabled`にするのは制作上の仮置き。月選択の下限は確定だが、境界のボタン表示・注文がまだない場合の月選択は未確定
- 前月／翌月へ移動できる場合はリンクとし、`aria-label`・`title`に移動先の月（例：「前月（2026年9月）」）を含める。固定の年月・リンク先は実際の条件へ置き換える

補足文は現在のPHPでは期間指定中→最初の注文月→今月の順で判定する。表示するときだけ`p#sales-month-help`と月セレクトの`aria-describedby="sales-month-help"`を出す。

| 条件 | 補足文 |
|---|---|
| 今月 | 今月より先の月は選べません。 |
| 最初の注文月 | 最初の注文月のため、前月は選べません。 |
| 期間指定中 | 期間指定中です。月の操作は、月単位の集計に戻るための操作です。 |
| 上記以外の月 | 文も月セレクトの`aria-describedby`も出さない |

期間指定中に月操作を残し、月表示へ戻ることを補足文で伝える形は仮置き。正式な戻し方・送信方法、片側入力・未入力時の扱いは未確定のまま（§10）。

- 期間指定は開始日・終了日の両日を含む。入力中は表示中の集計を維持し、「この期間で集計」で適用する想定。日付判定・検証はバックエンドで行う
- 逆転エラー文は「終了日は開始日以降の日付を指定してください」。形式エラー文は商品一覧と同じ「日付を正しく入力してください」。形式エラー専用previewはない
- エラーは`p.form-error#sales-date-error`の1つだけを終了日の入力欄の下（左端）から表示する。現行Sassでは終了日の列から集計ボタンの右端までを使う
- 両入力`#sales-from`・`#sales-to`に`aria-invalid="true" aria-describedby="sales-date-error"`を付け、同じエラー文に関連付ける。正常時はエラー用の属性・文を出さない
- エラー時も入力値と適用前の条件を残す想定。逆転の制作例は入力2026/10/20〜2026/10/10、表示中の集計・CSVの適用条件は今月のまま。形式エラー時の値保持も画面資料の案に沿って組み込む

## 5. 操作と条件の保持

- 月・店舗・並び順のセレクトは`data-auto-submit`を維持する（2026-10-22、Kenの決定）。共通`common.js`の`change`→`select.form.requestSubmit()`で所属フォームを送信する。画面専用JS・`noscript`の表示ボタンは置かない。詳細は[共通申し送り§4](HANDOFF_CLIENT_COMMON.md#4-commonjsの詳細検索とアコーディオン)
- 月の変更では店舗・並び順、店舗の変更では期間・並び順、並び順の変更では期間・店舗を保ち、1ページ目へ戻す。期間指定の適用でも店舗・並び順を保ち、1ページ目へ戻す想定。hiddenに適用済み条件を復元し、変更時にページ番号を送らない
- 並び順だけを変えた場合は合計を変えない。ページ送りでも期間・店舗全体の合計を保つ
- 店舗の初期値は「すべての店舗」。`orders.store_id`で絞り込む。店舗が1つのパートナーでは店舗セレクトを出さず、現行は店舗名を表示する。CSV・ページ送りにもその店舗を保持する
- CSVは「CSVをダウンロード」の副ボタン。入力中の日付ではなく、適用済みの期間・店舗で画面の合計と商品表を出力する。注文者の氏名・連絡先などの個人情報は含めない。現行の`.csv-form`は適用済み条件をhiddenで保持するだけで、CSV生成は未実装

| 操作 | 制作用のname・value／条件の保持 |
|---|---|
| 月 | `month`（例：`2026-10`）。hiddenは`store`・`sort` |
| 期間指定 | `from`・`to`。hiddenは`store`・`sort` |
| 店舗 | `store`（`all`または店舗ID）。hiddenは適用済みの`month`または`from`・`to`と`sort` |
| 並び順 | `sort`（`sales`／`quantity`）。hiddenは適用済みの期間と`store` |
| CSV | `download=csv`と、適用済みの期間・`store`・`sort` |
| ページ送り | `page`と、適用済みの期間・`store`・`sort` |

フォームはGET、送信先は制作の`sales.php`（静的出力時は`sales.html`）。パラメータ名・値・送信先は仮で、正式名とルートはバックエンドで決めてよい。変えた場合はフロントへ知らせてほしい。期間指定から月表示へ戻る操作の細部は§4の未確定事項と区別する。

## 6. 並び順とページ送り

- 初期は売上の多い順。表の右上の「並び順」で販売個数の多い順に切り替える。昇順・購入回数順は追加しない。同じ数値の商品の順序は未確定
- 全商品を対象に1ページ50件。上位N件に限定しない。制作の10行抜粋・426商品・9ページは実データへ置き換える
- [共通申し送り§7](HANDOFF_CLIENT_COMMON.md#7-ページ送り)の番号・省略記号・前後リンク・読み上げ名・現在ページの`aria-current="page"`に従う。各リンクに適用済み期間・店舗・並び順を引き継ぎ、`.count`と`.page-status`も実際の範囲・ページに同期する
- 1ページだけの場合にページ送りを出すかは未確定

## 8. JSと読み込み

- JSは`common.js`のみ。集計専用JSは作っていない。`</body>`直前に1回読み込み、月・店舗・並び順の自動送信に使う
- CSSは`common.css`→`sales.css`。固有Sassは`sales.scss`で、resetを重複させない。共通headのサイドバー初期化・読み込み順・キャッシュ対策は[共通申し送り§2](HANDOFF_CLIENT_COMMON.md#2-headの読み込みと初期化)・[§8](HANDOFF_CLIENT_COMMON.md#8-cssjsの読み込み順とキャッシュ対策)を参照

## 9. バックエンドで決めてほしいこと

[SPECの同節](../SPEC.md#バックエンドで決めてほしいこと)の6項目は、`QA_BACKEND.md`には載せず、バックエンドで決めて実装してよい（2026-10-22、Kenの決定）。決めた内容はフロントへ知らせてほしい。フロントがSPEC・画面資料へ反映する。将来の拡張に関する項目も含まれるため、現行の確定した集計条件と区別する。

| 決めてほしいこと | フロントの前提（今の画面・表示の想定） |
|---|---|
| 発送日・入金日を持つ列がない前提で、将来発送日で集計する場合に「発送済」にした日時を別に記録するか・記録方法 | 現行は受注日（`orders.ordered_at`）で集計する。発送日・入金日を選ぶUIはない。`shipping_status_updated_at`は最終更新日時なので発送日に代用しない |
| `shipping_status`の保存値と画面の5状態の対応、およびキャンセル・返品の判定に使う値 | 画面の5状態は「新規受付／対応中／発送済／返品対応／キャンセル」。集計は「キャンセル」「返品対応」を除外し、件数も出さない。正式な呼称・選択肢は未確定で、表示名から保存値を推測しない |
| キャンセル・返品になった日時と、状態を戻したときの履歴を持つか・保持方法 | 現行は後日の変更で受注日の期間の数字が変わり得る。過去の数字を固定するUI・集計方式は採用していない。履歴は、過去の数字が変わるのを避ける方式を検討する場合の論点 |
| 商品明細ごとの一部返品・返金額を持つ予定の有無 | 現行DB設計についてSPECに記載された前提は注文単位の発送状況のみ。一部返品・返金額は持たず、画面も注文単位の除外で作っている |
| `orders.purchase_group_key`の確定・必須化と、Clientの範囲で「同じ購入」を判定する方法 | 顧客一覧の購入回数の数え方に関わる。集計の注文件数は店舗ごとの注文数、商品ごとの購入回数はその商品を含む注文数で確定しており、このキーで数え直す想定ではない |
| `orders`・`order_items`のマイグレーションの作成予定と、集計画面を組み込む時期との関係 | SPECが参照するDB設計の「実装記録」には両マイグレーションの記載がないという前提。制作画面は固定例のみで、実データ取得・集計・CSV生成はバックエンドで組み込む。現在の作成状況をこの申し送りで確定しない |

## 10. 未確定のまま残っている項目

業務上の詳細は[SPECの集計の未確定事項](../SPEC.md#集計の未確定事項)、画面側の詳細は[画面資料の未確定事項](../design/CLIENT_SALES.md#未確定事項)を参照。バックエンドに関係する残りは以下のとおり。§9の決定依頼と、フロントで決める画面の論点を混同しない。

- CSVの文字コード（UTF-8／Shift_JIS）・ファイル名
- 発送状況の正式な呼称・選択肢。保存値の対応・キャンセル／返品の判定値は§9でバックエンドに決定を依頼する
- 将来、月別の推移（直近12か月など）を足すか。現行では置かない
- Masterでの対象パートナーの切り替え・絞り込み。Client画面には追加しない
- 期間指定中の月操作の見え方・月指定へ戻す操作と送信方法、日付の片側入力・未入力時の扱い
- 同じ売上・販売個数の商品が並ぶときの順序
- 1ページだけの場合のページ送り
- 商品画像の有無、商品名から商品詳細へのリンクの有無。現行は両方付けていない
- CSV出力中の表示・操作抑止・失敗時の案内、売上がない場合のボタン。空・取得失敗での無効表示は仮置き
- 前月／翌月の無効表示の最終確認、最初の注文月での前月無効の扱い、注文がまだない場合の月セレクト
- 取得失敗の部品。現行は店舗一覧を参考にした`.list-empty.list-error`で、共通部品としては未確定

合計の単位・揃え・箱の寸法、表の列幅、将来の共通部品化は画面資料側に残る。現行のマークアップ・Sassを基準にし、未確定の見た目を業務仕様の確定と扱わない。
