# デザイン方針

## 目的

ECサイト運用者が、情報量の多い業務でも迷わず確認・入力・更新できる管理画面を作る。

## 基本方針

- 情報の優先順位を、見出し、余白、配置、文字サイズで明確にする
- 装飾を増やしすぎず、データと操作を主役にする
- 主要操作、補助操作、危険操作の見た目を分ける
- 画面ごとに独自ルールを作らず、共通コンポーネントを利用する
- 色だけに依存せず、ラベル、アイコン、文言を併用する
- 行ごとに繰り返す操作はピクトグラム。画面に1つしかない操作と、保存などの確定操作は文字ボタン、ページ移動や解除は文字リンクとする
- ナビ・ヘッダー・見出しには飾りのアイコンを付けない。色や形だけに依存しないよう、ピクトグラムにはアクセシブルな名前とツールチップを付ける。開閉操作には開閉状態も設定する
- 実装難易度を理由に必要なデザインを簡略化しない
- 静的HTML・Sassをブラウザで確認しながらデザインを固める。Figmaは必要な場合のみ使用する

## 管理画面のバリエーション

管理画面は次の2種類を対象にする。

- `Master`：マスター管理画面
- `Client`：クライアント（代理店）管理画面

共通UIの構造とスタイルを基準にし、管理画面種別ごとの差分は各管理画面のSassと表示内容で管理する。共通Sassはルートの`scss/`に置き、各管理画面から`@use`で読み込む。

### 共通にするもの

- Input、Select、Textareaなどのフォーム部品
- ボタンのサイズ、余白、角丸、基本状態
- タイポグラフィとスペーシング
- ヘッダー、サイドバー、ページヘッダーの基本構造
- テーブル、モーダル、アラートなどの操作方法

### 種別ごとに変更できるもの

- アクセントカラー
- サイドバー背景（淡いブランド色）
- ロゴ、サービス名、管理画面名
- ナビゲーション項目
- 表示コンテンツと操作権限
- 種別を識別するラベルや補助表示

色だけに依存せず、管理画面名やラベルでも現在の種別を識別できるようにする。

### ブランド色とステータス色（仮方針）

- 熊日ロゴの青・緑だけをブランド色の基準とする。[提供ロゴSVG](reference/kumaniti-logo.svg)で外枠ほかの青`#0080CB`、Kマークの青`#008BD5`・緑`#00BC64`を確認済み。これらは基準の参照用で、UIでは直接使わない。正式なコーポレートカラーの指定値とMaster＝青／Client＝緑の割り当ては、引き続き熊日に確認する
- 「濃い色の塊＝ステータス、淡い面と細い線・文字＝ブランド色」と役割を分ける。ブランド色は濃い面を塗る用途に使わない。例外はヘッダーのログアウトボタンだけで、ほかのボタンには広げない
- Clientはサイドバー背景`#EEF9F4`、線・文字・KPI選択・リンク`#097141`。Masterは背景`#EEF5F9`、線・文字`#0D679C`。ロゴの色みを基にしたUI用の仮値で、選択ナビは白い背景＋ブランド色の左バー・文字とする。JPEG近似値とそれに基づく旧仮値はトークン資料の履歴に残す
- ステータスは青・緑を避け、対応が必要なものほど強い色、終わったものは落ち着いた色とする。状態名・選択肢・配色の割り当ては未確定。仮値とコントラストの注意点は[DESIGN_TOKENS.md](../../DESIGN_TOKENS.md)で管理する
- 白文字を使う背景はコントラスト4.5:1以上を条件とする。SVGの基準色はこの条件を満たさないため白文字の背景に使わない。UI用の仮色のコントラスト値はトークン資料を参照する
- キャンセルは白背景＋1px枠`#6B6B6B`＋文字`#6B6B6B`（白との比は約5.33:1）の塗りなし表示とする。キャンセルされた注文であることを形でも示し、塗りのある発送済（墨`#4A4F57`）と区別する。旧仮背景は白文字不可のため変更し、履歴に残す。状態名・選択肢・配色値は引き続き未確定
- Client / Masterは淡いサイドバー背景とヘッダーの管理画面名を組み合わせて区別する。正式名称が決まるまでヘッダーの仮表記「熊日モール」を維持する
- ロゴ画像は色の参考だけに使い、ヘッダーには配置しない。キャラクターとその色（`#009E38`・黄・ピンク・ベージュ）は管理画面のUI・配色に使用しない
- Clientの実装・表示確認を優先する。Masterは仮値の定義だけとし、表示確認はMaster画面の制作時に行う。今回の方針変更は資料のみで、画像・HTML・Sassは変更しない

## Figmaを使用する場合

必要になった場合のみ既存Figmaを確認し、構成を決める。以下は任意の参考案とし、現時点では作成しない。

ページ構成の参考：

1. `00 Cover`
2. `01 Foundations`
3. `02 Components`
4. `10 Master Screens`
5. `11 Client Screens`
6. `90 Archive`

- Figmaへ反映する前に既存構造を確認し、`figma-use`を使用する
- 画面と主要ブロックにAuto Layoutを使用する
- 共通部品はComponents / Instances、状態差はVariants / Properties、色差はVariables Modeで管理する
- Variables / Stylesは`DESIGN_TOKENS.md`と名称・値を揃える
- 反映後はスクリーンショットで表示を確認する

## レイアウト

- 共通ヘッダー、サイドバー、メイン領域の構造とスタイルを揃える
- 画面全体と主要ブロックは、内容に応じてCSSのFlexboxやGridで配置する
- 固定幅と可変幅を区別し、画面幅が変わったときの挙動を設定する
- テーブルやフォームでは、ラベルと値の対応が崩れないようにする
- 基準幅は要件確認後に確定する
- 画面固有の詳細は[CLIENT_ORDER_LIST.md](CLIENT_ORDER_LIST.md)を参照する

## コンポーネント

- ボタン、入力、選択、タグ、アラートなどの状態は、適切なHTML属性、疑似クラス、状態classで表現する
- Default / Hover / Focus / Disabled / Errorなど必要な状態を用意する
- 同じ用途のコンポーネントを画面ごとに複製しない
- コンポーネント名は役割が分かる名前にする

### フォームコンポーネント

- `Input / Text`
- `Input / Textarea`
- `Select`
- `Checkbox`
- `Radio`
- `Date Picker`
- `File Upload`

最初に使用する画面で、サイズ、ラベル、補助説明、必須表示、エラー表示、各状態を確認する。確定した構造とスタイルを共通仕様に整理し、各画面で同じルールを使用する。

画面固有の見た目が必要な場合も、既存の共通仕様の拡張で対応できないかを先に確認する。類似部品や画面専用の上書きを安易に増やさない。

## トークン

- 共通値は`DESIGN_TOKENS.md`を基準にする
- 共通SassとMarkdownのトークン名称を揃える。Figmaを使用する場合も同じ名称を使う
- 値を追加・変更した場合は利用箇所を確認する

## 画面確認

- 変更前に既存HTML・Sassとブラウザ表示を確認する
- 変更後はブラウザで全体と主要状態を確認し、必要に応じてスクリーンショットを残す
- 文字切れ、レイアウトの崩れ、意図しない重なりや横スクロールがないか確認する
- 一度に複数画面を大きく変更せず、画面単位で確認する
