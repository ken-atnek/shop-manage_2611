# デザイン方針

## 目的

ECサイト運用者が、情報量の多い業務でも迷わず確認・入力・更新できる管理画面を作る。

## 基本方針

- 情報の優先順位を、見出し、余白、配置、文字サイズで明確にする
- 装飾を増やしすぎず、データと操作を主役にする
- 主要操作、補助操作、危険操作の見た目を分ける
- 画面ごとに独自ルールを作らず、共通コンポーネントを利用する
- 色だけに依存せず、ラベル、アイコン、文言を併用する
- 実装難易度を理由に必要なデザインを簡略化しない

## 管理画面のバリエーション

管理画面は次の2種類を対象にする。

- `Master`：マスター管理画面
- `Client`：クライアント（代理店）管理画面

共通コンポーネントを基準にし、管理画面種別ごとの差はVariant、Component Property、VariablesのModeなどで管理する。

### 共通にするもの

- Input、Select、Textareaなどのフォーム部品
- ボタンのサイズ、余白、角丸、基本状態
- タイポグラフィとスペーシング
- ヘッダー、サイドバー、ページヘッダーの基本構造
- テーブル、モーダル、アラートなどの操作方法

### 種別ごとに変更できるもの

- アクセントカラー
- ロゴ、サービス名、管理画面名
- ナビゲーション項目
- 表示コンテンツと操作権限
- 種別を識別するラベルや補助表示

色だけに依存せず、管理画面名やラベルでも現在の種別を識別できるようにする。

## Figmaの構成

既存Figmaを確認してから確定する。

推奨ページ構成：

1. `00 Cover`
2. `01 Foundations`
3. `02 Components`
4. `10 Master Screens`
5. `11 Client Screens`
6. `90 Archive`

## レイアウト

- 共通ヘッダー、サイドバー、メイン領域をコンポーネント化する
- 画面全体と主要ブロックにはオートレイアウトを使用する
- 固定幅と可変幅を区別し、リサイズ時の挙動を設定する
- テーブルやフォームでは、ラベルと値の対応が崩れないようにする
- 基準幅は要件確認後に確定する

## コンポーネント

- ボタン、入力、選択、タグ、アラートなどは状態をVariantsで管理する
- Default / Hover / Focus / Disabled / Errorなど必要な状態を用意する
- 同じ用途のコンポーネントを画面ごとに複製しない
- コンポーネント名は役割が分かる名前にする

### フォームコンポーネント

- `Input / Text`
- `Input / Textarea`
- `Select`
- `Checkbox`
- `Radio`
- `Date Picker`
- `File Upload`

最初に使用する画面で、サイズ、ラベル、補助説明、必須表示、エラー表示、各状態を確認する。確定したコンポーネントは`02 Components`で管理し、各画面ではInstanceを使用する。

画面固有の見た目が必要な場合も、既存コンポーネントのPropertyやVariantで対応できないかを先に確認する。安易にDetachした部品や類似コンポーネントを増やさない。

## トークン

- 共通値は`DESIGN_TOKENS.md`を基準にする
- Figma Variables / StylesとMarkdownの名称を揃える
- 値を追加・変更した場合は利用箇所を確認する

## 画面確認

- 変更前に対象フレームと親子構造を確認する
- 変更後はスクリーンショットで全体と主要状態を確認する
- 文字切れ、Auto Layoutの崩れ、意図しない絶対配置がないか確認する
- 一度に複数画面を大きく変更せず、画面単位で確認する
